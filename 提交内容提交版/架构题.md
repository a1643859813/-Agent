## 架构设计题

### 模块一：Context / Performance

#### 2. 一个 session 连续聊了 200 轮，context 快爆了。你会怎么做压缩？如何确保压缩后的对话仍然流畅？

我会把“历史消息”与“当前模型上下文”分开设计。原始历史完整保存，但模型每轮只拿到预算内最有用的信息。

```text
System Prompt
+ 当前 Run 状态（目标、约束、已完成、下一步）
+ 相关长期记忆
+ 结构化历史摘要
+ 最近 10-20 轮原文
+ 当前输入 / 本轮工具结果
```

当历史超过 Token 阈值，例如上下文预算的 60% 时，后台将较早消息压缩为结构化状态，而不是一段泛泛摘要：

```text
目标：实现 Agent Runtime
已确认决策：同一 Session 串行执行
约束：不依赖 Agent 框架
未完成：补充异步工具恢复策略
关键事实：用户偏好 Java 示例
证据：messageId 列表
```

这里有三个关键取舍：

1. 保留最近原文，保证“刚才那个”“继续做”等指代自然。
2. 旧历史按需检索，只把与当前问题相关的片段放进 Prompt。
3. 摘要必须保留来源和时间。相对时间如“今天”要转换为绝对日期，防止跨天后产生误判。

摘要一定会损失细节，所以原始记录不能删除；用户追问细节时，可按来源 ID 回查。长上下文实践更适合采用“滑动窗口 + 摘要 + 精准筛选”，而不是无上限堆历史。

### 模块二：Memory

#### 和聊天 Agent 熟悉半个月后，用户问了一个以前问过的问题。Agent 如何做 memory 召回更合理？

我的原则是：Memory 不是“历史聊天全文”，而是经过筛选、带时效和来源的可复用信息。

我会拆成三类：

- **用户档案**：稳定偏好、身份、长期目标。
- **任务记忆**：进行中的任务、关键决策、未完成事项。
- **历史结论**：以前问过的问题、当时答案、依据、产生时间和适用条件。

每条记忆至少保存：

```text
memoryId、userId、type、content、sourceMessageIds、
importance、confidence、createdAt、lastVerifiedAt、validUntil
```

召回流程：

```text
当前问题
→ 是否需要历史信息
→ 仅检索当前 userId
→ 关键词 + 向量混合检索
→ 按相关性、重要性、时效性、可信度重排
→ 去重与冲突处理
→ 召回 Top K
→ 结合当前事实重新推理
```

例如用户之前问过“Java 是否适合做 Agent 服务”，今天再问时，可以召回“团队主要使用 Java”这一稳定约束；但旧的技术选型结论不能直接复用，因为模型能力、团队要求、性能目标可能已经变化。

冲突处理上，新且高可信的信息覆盖旧信息；低可信信息保留为候选，不直接覆盖。用户可以查看、修改、删除自己的长期记忆。

### 模块三：Task

#### 2. 用户要求每天早上 9 点根据昨天聊天情况做复盘总结，如何设计？

我会把它设计成持久化的定时任务，而不是在某个 Session 内挂一个计时器。

```text
Task Definition
→ Scheduler 计算触发时间
→ 创建唯一 TaskRun
→ Worker 拉取昨天聊天
→ 脱敏、过滤已删除数据
→ 分 Session 分片摘要
→ 汇总生成日报
→ 保存结果
→ Notification 投递
```

任务定义应保存：

```text
taskId、userId、timezone、cron、scope、promptTemplate、
catchUpPolicy、retryPolicy、status、version
```

关键问题的处理：

- **时区**：优先使用用户设置；缺失时要求确认，不能使用服务器时区。
- **多个 Session**：先分别摘要，再汇总，避免不同话题互相污染。
- **聊天过长**：按 Session 和 Token 分块摘要，不能一次性将全部原文交给模型。
- **没有聊天**：生成“昨日无有效聊天记录”，或按用户偏好不提醒。
- **宕机错过 9 点**：定义 `catchUpPolicy`，例如在两小时内补跑一次，超时则跳过并记录。
- **重复触发**：以 `(taskId, scheduledAt)` 作为唯一键，确保同一周期只生成一个 TaskRun。
- **LLM 或通知失败**：指数退避重试；达到上限后进入失败队列并告警。
- **修改任务**：任务配置版本化；已运行的 TaskRun 使用旧版本，后续任务使用新版本。
- **隐私**：只读取尚未删除且用户授权的数据，进入模型前完成脱敏。

定时系统不能只讲 Cron，必须讲错过触发、幂等、重试、执行记录和补偿策略。

### 模块四：Tool / Session Runtime

#### 2. 如果 session state 为 busy，此时用户又发来新消息，或者异步工具完成事件也到达，runtime 应该如何处理？

采用“同一 Session 串行，不同 Session 并行”。

所有输入都先事件化，再进入按 `sessionId` 分区的队列。同一 Session 由唯一 Executor 顺序消费，避免用户消息、异步回调、工具重试同时修改 Context。

```text
事件：
eventId、sessionId、runId、toolCallId、type、payload、createdAt

状态：
IDLE → RUNNING → WAITING_TOOL → RUNNING → COMPLETED
                         ↘
                  CANCELLED / FAILED / TIMEOUT
```

用户消息分三类：

1. **补充当前任务**：例如“分析时重点看 Session 模块”。写入 Run 的新增约束，在下一个安全点生效。
2. **修改或取消**：例如“停止发邮件”。作为高优先级控制事件，标记 `CANCEL_PENDING` 或 `REDIRECT_PENDING`。
3. **无关问题**：进入队列，当前 Run 完成后再创建新的 Run。

异步工具结果的处理：

- Run 正在等待该工具：校验 `runId + toolCallId` 后写入结果，恢复 Loop。
- Run 已终态：标为迟到结果，只保留审计记录或通知，绝不复活旧 Run。
- Session 正在跑其他任务：先落库，待安全点决定通知或处理。

系统采用“至少一次投递 + 幂等消费”，不承诺不现实的全局 exactly-once。用 `eventId` 或 `toolCallId` 做去重，并按 `sessionId` 保证局部有序。消息重复、乱序与重试是异步系统的常态，不是异常分支。

### 模块五：Agent Runtime 架构对比

#### 1. Claude Code 的工具输出方式和国内 GLM / 豆包等 OpenAI-compatible function calling 有什么不同？他们各自这样设计的优缺点是什么？

先明确：Claude Code 是完整的 Coding Agent Runtime；GLM、豆包等 OpenAI-compatible Function Calling 主要是模型工具调用协议。两者不在同一抽象层。

不能简单说 Claude 用 XML、OpenAI-compatible 用 JSON。两者的工具参数定义核心都是 JSON Schema；真正区别在于消息结构、流式行为和 Runtime 能力边界。

我的架构不会让业务逻辑直接依赖厂商格式，而是定义内部统一对象：

```text
ToolCall
ToolResult
RunState
ToolDefinition
```

然后分别实现 Anthropic Adapter、OpenAI-compatible Adapter。适配层负责消息转换和流式参数拼装；Runtime 统一负责：

- 参数 Schema 校验；
- 权限确认；
- 超时和重试；
- 并行/串行工具调度；
- 幂等与审计；
- 错误归一化和降级。

这样以后替换模型时，影响被限制在 Adapter，而不是扩散到整个 Agent Runtime。这里最值得在笔试中强调的一点是：OpenAI-compatible 表示接口接近，不表示工具调用的并发、流式参数、JSON 合法性与错误行为完全一致。

| 维度 | Claude / Anthropic 风格 | OpenAI-compatible 风格 |
| --- | --- | --- |
| 调用表示 | 内容块中的 `tool_use` | assistant message 中的 `tool_calls` |
| 结果回传 | `tool_result` 与调用 ID 关联 | `role=tool` 与 `tool_call_id` 关联 |
| 工具定义 | JSON Schema | JSON Schema |
| 产品能力 | 通常整合权限、文件、Shell、上下文管理 | 多数只提供协议，Runtime 自建 |
| 适配成本 | 更贴近自身生态 | 更容易接入多模型与框架 |
